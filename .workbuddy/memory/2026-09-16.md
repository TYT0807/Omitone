### 五、浏览器 E2E 的五个坑（写进 tools/README）

1. **必须成对**用 `--disable-extensions-except` + `--load-extension`。
   新版 Chromium 单独给 `--load-extension` 常被静默忽略 —— 症状是 target 列表里
   只有 Edge 自带的 5 个扩展、我们的完全不加载。
2. **扩展 ID 要算，不要去 CDP 里等**。MV3 service worker 懒启动，不一定出现在 target 列表。
   算法：`SHA256(扩展目录绝对路径)` 前 32 位十六进制逐位映射 `0-f → a-p`；
   **Windows 上路径按 UTF-16LE 参与哈希**（不是 UTF-8）。这是用 `tools/ext-id.js`
   拿真实 ID 反推出来的。
3. **不能用 `fetch("chrome-extension://…")` 探测**资源 —— 浏览器禁止网页脚本
   fetch 非 http(s) scheme，永远 false（`<script src>` 才行）。
4. **收尾必须杀整个进程树**（Windows `taskkill /PID x /T /F`）。只 `kill()` 主进程
   会残留实例继续占 CDP 端口，下次运行连到**旧实例**上，症状是"所有候选 ID 都注入失败"。
5. **跨域脚本异常必须走 CDP `Runtime.exceptionThrown`**。`page.js` 对 http 页面是跨域脚本，
   页面里挂 `window.onerror` 只能拿到 `Script error.`。
6. 另：CDP `/json/new` 只接受 **PUT**。

## 第 22 轮：提示词 v2 —— 位置式输出 + 分批 10 题（1.0.11 内）

### 一、GitHub 对照（CodFrm/cxmooc-tools）

看了 `src/internal/app/question.ts` 与 `src/mooc/chaoxing/question.ts`：

- **题型体系**：`-1 错 / 1 单选 / 2 多选 / 3 判断 / 4 填空` —— 注意它**没有独立的
  简答类型**，简答被归到填空或不支持。我们区分 `short` 是对的（textarea 与 input 不同）。
- **题库接口一批发 20 题**（`let num = 20`）。我们才 5 题 → 拉大分批量是安全的省 token 方向。
- 答案是纯值对象，不是带键名的包装结构。

### 二、token 优化结果（实测，40 题整卷）

| 版本 | 分批 | 输入 | 输出 | 合计 | 相对 1.0.10 |
|---|---|---|---|---|---|
| 1.0.10 | 5 题/批 | 3448 | 744 | 4192 | — |
| v1（首版） | 5 题/批 | 2480 | 376 | 2856 | 省 31.9% |
| **v2（当前）** | **10 题/批** | **1904** | **172** | **2076** | **省 50.5%** |

两项改动：
1. **输出改成纯位置式数组** `["A",["A","C"],true,"x|||y"]`，不再回传 `i`/`a` 键名。
   每题输出约 11 token → 约 5 token。位置对齐本来就是 content.js 在 index 缺失时的
   兜底行为，现在把它提升为唯一协议。
2. **分批 5 → 10 题**。system 与格式示例是每批重发的固定开销（约 88 token/批），
   题目正文只发一次；40 题从 8 批降到 4 批。

### 三、为"压缩不压掉正确性"加的保险

- `normalizeItem` 三种输入形态各一条断言。**位置式数组是最容易写错的一例**：
  数组的 `typeof` 是 object，若被当成 `{a:…}` 包装对象解析，
  多选答案会被整条丢掉。
- 新增 `coerceAnswerForType`：单选收到 `["A"]` 解包成 `"A"`、
  判断题收到 `"正确"`/`"T"` 归一成 `true`；**多选数组必须原样保留**。
  不做这层规整的后果是匹配不上 → 该题静默不填 → 永不提交。
- 输出长度与题目数不符 → 记 `llm answer count mismatch` 日志 + 按位置对齐；

## 第 23 轮：多讨论任务点 + 跳过不必做的任务点（1.0.11 内）

用户反馈两个真实现象：
① **多个"沟通"（讨论）任务可能出现 bug**；
② **有些任务不需要完成，老师会安排"不可滑动"来挡住插件，浪费时间**。

### 一、多讨论任务点：三处真实缺陷

1. **`#isFinished` 用了文档级查找**。`_collectDiscussionTargets` 在卡片循环里调
   `doc.getElementById('isFinished')` —— 一个章节里多张讨论卡片若落在**同一个文档**中，
   会共用同一个"已完成"标志：第一张已完成则其余**永久跳过**（反之反复重开同一个）。
   → 改为按卡片范围查找，且**必须先在祖先上判断卡片数量再读标志** ——
   顺序反了就会在"多卡片共用容器"上读到共用值，原 bug 原样复发（我第一版就写反了，
   自己回读时发现）。
2. **去重键用 `url.slice(-70)`**。两个任务地址若只有前段不同、后 70 字符相同就碰撞 →
   第二个被判"24 小时内已处理"而**永久漏做**。
   → 改为优先取唯一 `mtopicid`，取不到退回整条 URL 的 djb2 哈希。
3. 兜底路径的 `名称 + href.slice(-40)` 同样会碰撞，一并改哈希。

**安全性权衡**：卡片范围找不到标志且同文档有多张卡片 → 按**未完成**处理
（宁可重复问也不漏做）；只有一张卡片时保留旧的文档级查找，行为不变。

### 二、跳过不必做 / 做不完的任务点

**GitHub 对照给出权威判据**（`cxmooc-tools` 的 `src/mooc/chaoxing/task.ts`）：

```js
if (this.taskinfo.job) { this.done = false }   // 是任务点 → 要做
else { this.done = true }                       // 不是任务点 → 直接跳过
```

它**不靠模块名推断**。由此发现我们的真 bug：

- **`job: false` 被误当成任务点**。`_getAttachmentWorkType` 里 `job === true` 有分支，
  但 `job === false` 会**直接落到"按模块名推断"**那段 → 老师没设为任务点的视频/文档
  又被推断成 `job`，插件白做一遍。这正是用户说的"有些任务不需要完成，插件却去做"。
  → 显式 `false`（含字符串 `"false"`）在此处直接 `return 'not-job'`；
  `_buildAttachmentOnlyJob` 返回 null；`_classifyTaskFrame` 识别帧数据的 `"job":false`。

- **新增"做不完就放弃"**：防拖拽视频、不可翻页文档、不计分摆设，
  插件对这些只会一次次重试。现在每派发一次就检查是否真的完成，**没完成才计数**；
  连续 `taskGiveUpAttempts` 次（默认 4）未完成 → 记入 localStorage（24h）+ 跳过 + warn 日志。
  **安全点：`_isJobCompleted` 拿不准时一律返回 `true`** ——
  误判成"没完成"会把必做任务点跳过，比多跑一次严重得多。
  - 新增 `xxtAI.taskGiveUpList()` / `xxtAI.clearTaskGiveUp()`。
  - `taskGiveUpAttempts` 按 `playbackRateCap` 的先例做成"配置项但无 UI"。

### 三、测试

e2e 从 12 场景 / 100 项 → **14 场景 / 129 项**：
- 新增「多讨论任务点」：4 张卡片（3 张共用容器 + 1 张独立，尾串刻意做长以暴露 `slice(-70)` 碰撞），
  断言去重键互不相同、不误用容器级标志、独立卡片仍正确判已完成、挑出未完成那个
- 任务类型识别新增 7 项 `job:false` 断言（5 模块 + 字符串形式 + `job:true` 反向验证）
- 新增「做不完的任务点跳过」：键、阈值、名单读写与清除、`_isJobCompleted` 保守性

### 经验沉淀

- **开源实现里的一行 `if` 往往就是权威判据**。`if (taskinfo.job) … else …`

## 第 26 轮：效率与 token 优化（空答案补问）+ 测试脚手架扩展 ID 修复

### 一、卡住的根因（上一轮已修，本轮回顾确认）

`_detectQuiz` 的 `if (title.indexOf('考试') !== -1) return true` 把标题含"考试"的章节

修法是**判定必须有 URL 链证据**（work/exam 页特征）。

### 二、本轮的核心 token 优化：空答案补问

旧行为：模型偶尔对某题返回空答案 → `page.js._avoidKnownWrongAnswer` 走到**空答案兜底 →
猜第一个选项**；判断题猜错概率 50%，猜错触发**整卷带 `禁:` 前缀重答**（几百 token + 一整轮
页面往返）。现象就是日志里反复出现 `llm empty answer fallback`。

现在 `content.js.handleLLMRequestDirect` 在一轮跑完后，**只对没拿到答案的题**打包成一次
小请求重问（日志 `llm refill unanswered` / `llm refill failed`）。把"猜"换成"问"。

实现要点（易错处，已写进代码注释）：

- 只在**部分成功**时补问：全失败说明 API/解析本身有问题，重试再多也是白烧
- 主批与补问共用抽出来的 `mergeAnswers`，对齐规则不会漂移（不要复制粘贴）
- 补问失败不会污染 `apiConnectionFailed`：后面的成功分支会把它重置回来（顺序很重要）
- 重复 index 不会误触发补问（`unfilled` 二次过滤）

顺手：DeepSeek 加 `thinking:{type:'disabled'}`（仅 DeepSeek，其他兼容服务会 400），
实测 2 题 361 → 133 token；`submit confirm key mismatch` 从 warn 降为 info（良性，易误导排查）。

> 本轮**没有**继续压缩提示词本身：v2 已到 47.1 tokens/题（相对 1.0.10 省 50.5%），
> 再压主要是每批 ~88 token 的固定开销，而学习通章节测验通常是 5~10 题 = **本来就只有 1 批**，
> 等于零收益。真正的 token 大头是"猜错导致整卷重答"，补问正是打这里。

### 四、测试脚手架：扩展 ID 不再靠"算"（e2e 全线失败的真正原因）

e2e 14 个场景全部报「page.js 在真实 Edge 中加载成功：失败」，页面里**一条异常都没有**。

target 列表里有我们的 background.js）。真因是：

```
真实 ID： hdlemlcmf… ← SHA256("D:\Omite", utf16le)  大写盘符
算出 ID： locncobd… ← SHA256("d:\Omite", utf16le)  小写盘符
```

里的 `origin`（最可靠，content script 每个页面都跑）② `/json/list` 里 title 含 Omitone 的 target
③ 路径哈希兜底。不一致时打印警告。**改完立即 135/135 全绿。**

这类"测试方法本身的错误伪装成产品 bug"最贵 —— 症状和"扩展坏了"一模一样，
但页面里干净得看不出任何线索。判断口诀：**先看 e2e 输出的「扩展 ID:」那一行，再怀疑代码。**
