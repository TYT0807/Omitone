## 2. 模块职责与收益

此前日志元数据清洗、负载验证、队列和存储操作混在 `<仓库根>\\background.js` 中。拆分后：

| 文件 | 职责 |
| --- | --- |
| `<仓库根>\\runtime-log-store.js` | 负载验证、元数据脱敏、队列、追加/清空、容量与排队过期 |
| `<仓库根>\\background.js` | 真实发送者身份与作用域、带超时的 Chrome 存储操作、创建唯一日志服务实例并路由消息 |
| `<仓库根>\\omitone-log-store-test.cjs` | 不使用浏览器全局变量验证模块公共契约及部署守卫 |

公共接口：`create({ read, write, authorize, now })` 返回只暴露 `handle(message, sender)` 的实例。

- 模块不直接访问 `chrome`、DOM、网络、localStorage 或全局时钟。
- 每个实例拥有独立队列；宿主对同一存储键只能创建一个实例。多实例测试不等于生产允许多个写入队列。
- 权限在任务执行前通过宿主重新核验，只有明确返回 true 才允许读写。
- 宿主注入的 read/write/authorize 必须有界完成；实际 Chrome 调用沿用既有超时包装，模块没有叠加另一套计时器。
- 维持原 `runtime_log_append` / `runtime_log_clear` 消息、`runtimeLogs` 存储键、条目形状、200 条上限和 15 秒排队期限。

收益是可以直接替换存储/授权能力做单测，而不必同时模拟完整 Worker。此次不是性能优化，也不声称减少了整体代码量。

加载方式是 Worker 的 `importScripts('runtime-log-store.js')`；没有把模块加入页面注入或 web_accessible_resources，不扩大页面权限。

### Worker 依赖检查

`<仓库根>\\tools\check.js` 在既有文件检查中递归读取本地字面量 importScripts：

- 检查依赖存在、路径未越界、非外部 URL、纳入打包白名单。
- 按 Worker 入口 URL 解析相对路径，而不是按被导入文件的位置解析。
- 去重遍历，识别被 Worker 使用的文件，不把新模块误报为死文件。
- 动态 importScripts 路径不支持，要求显式本地字面量。

这是针对仓库写法的静态扫描，不是通用 JavaScript 解析器或安全沙箱。工程检查显示的引用数量从原始引用次数改为去重后的依赖文件数，不是减少测试覆盖。
